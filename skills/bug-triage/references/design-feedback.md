# 把建议记到合适的事项

适用于“找合适地方记录”“把这个交互建议记下来”。这是记录建议的委托；沿用当前明确项目、受众和已有授权，不再问一次是否要记录。仓库或披露范围确实不明时才补这个缺口，不向用户索要报障复现表。

## 找到上下文和落点

先 `feishu_read_thread` 读原话题，包括提出人的原话、后续澄清、已有方案及反对意见。下面读取当前话题；显式目标须成对传入真实 `chat`、`thread_id`。

```json
{"tool":"feishu_read_thread","arguments":{"limit":500}}
```

当前工具最多返回 500 条，没有翻页游标。仍截断或卡片不可读就保留缺口，不能声称已读完整、没人回复或没有现成方案；只对影响建议含义或记录落点的缺口继续查证。不要混入其他话题或私聊内容。

读回线程里的实际方案链接。需要判断现有实现、建议是否已支持、改动落在哪个模块时，核对获准 `repos/` 中相关函数、调用方及 commit；不能只凭文件名或最新代码断言用户现场行为。单纯记录建议不要求先完成实现或根因研究，未核实的可行性写待评估。

用 `github_list_issues` 在本次获准仓库按建议主题查重，显式给 `repo`、`type: issue`、`state: all`；默认 open 会遗漏已关闭的方案。对相关候选用 `github_get_issue` 读正文与评论，不能只靠同名匹配。结果被截断时收窄关键词继续查证，不将显示列表当作全库无重复的证明。

`github_get_issue` 也会截短正文和评论，最多带 50 条评论；只对实际读到的内容作判断，不据此宣称完整历史中从未讨论过。

- 同一事项已有 Issue：在获准记录范围内用 `github_comment_issue` 补上新建议；已有完全相同内容则直接复用链接，不重复评论。
- 相关但不同的建议：用 `github_open_issue` 建新事项，在正文引用已读回的方案链接并说明关系；不要改写旧方案或声称已经依赖、采纳。
- 没找到合适事项：在已明确的项目仓库建 Issue。只有已有本地报障案件时才用 `friday_bug_link_issue` 回填，不为设计建议另建 bug 桶或平行待办。

网关的权限与确认仍生效，技能本身不授予外部写权限。调用超时或结果未知时先查回真实状态，不换标题或重发来绕过未知结果；没有确认回执就说明尚未确认记录成功。

## 内容和真实人物

正文保留使用场景、要改善的问题、建议行为、相关方案和待评估点，引用原话注明提出人；未知内容不补成事实。保留谁来操作、何时触发、是否默认及并列要求：用户点击隐藏不能改成完成后自动隐藏，两项独立要求不能改成二选一。只用已读取或工具返回的真实 Issue、文档、话题链接。没有可验证消息链接时记录真实 message ID/thread ID 出处，不造 URL；公开正文不复制私密原文或原始附件。

提出人取该条建议消息的 `sender_open_id`，不能把转述人自动当成提出人，也不能凭显示名猜 open_id。候选负责人从当前成员资料、明确模块分工或相关 Issue 的真实 assignee 核实；仅有代码作者或参与讨论不足以称负责人。GitHub 身份用 `friday_whois` 核对当前群，只有 `resolved` 才原样使用返回 mention；其他三态不拼 @，无人选就保留待认领。成员资料不复制进技能。

GitHub `assignees` 只在人明确指派时填写；请求某人评估不等于已指派或对方已接手。提出人和负责人 @ 均需目标群成员的网关核验；网关退回普通姓名时，不声称已通知。

## 原话题短回执

完成后只回原话题，不主动发到其他群。用 1–2 个短句给实际动作、返回 URL、一句建议摘要，负责人已核实则请其评估；通常不展示内部工具名、源码路径或查重过程。

例如：「@提出人 已记到〈返回链接〉：〈建议摘要〉，并引用了〈已核实方案〉。请 @已核实负责人 评估。」其中 @ 使用真实身份标签；每个动作都须有工具回执或已核实的实际内容。补评论就说“已补充”，只复用就说“已有记录”，没关联方案就删去关联句，没有负责人就不编人，不把请评估说成已认领。
