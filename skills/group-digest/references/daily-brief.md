# 每日简报

用于用户当次索取的简报，或已登记的每日简报职责。先沿用已知日期、时区、关注范围和投递位置；今日安排按该日期，变化按职责给定窗口，未指定则取最近 24 小时并简短标注。只补影响执行的缺口，不要求用户逐条提供事项。

## 按需取当前事实

- `friday_todo_list` 用 `active` 取当前空间或本人已登记的进行中、阻塞、待验收事项，候选不当本人承诺。结果截断时按 `open`、`blocked`、`review` 分别收窄，必要时按 kind 或提高 limit（最多 100）；仍截断就说明未展示范围，不能说没有待处理事项。`friday_routine_list` 核对相关职责与暂停原因。职责下次运行是助手安排，不是人的会议或截止日。
- 群讨论用 `feishu_read_chat_history`，有关键结论再用 `feishu_read_thread` 展开；仅使用当前可读且允许向当前受众交付的来源。
- 群记录里的卡片（包括 Friday 自己发的职责提案、待拍板、确认卡）只代表发出那一刻；现在的状态以工具为准：职责用 `friday_routine_list`，待办和待拍板用 `friday_todo_list`。查不到当前状态就不提，不从卡片文字推断「还在等你点接受」。
- 项目进展按 `project-tracking` 用 `friday_project_view` 刷新获准仓库，明确事项再核对详情。保留同步时间与缺口；没有前次证据或明确事件时间，只能说当前状态，不能编造“新增”“刚完成”。
- 待本人评审的 PR 用 `github_list_issues` 查获准仓库：`type=pr`、`state=open`、`query=review-requested:<本人的 GitHub login>`。沿用本人明确提供且已与当前身份核对的 login；不确定账号时只补这一个缺口，不猜人名，不用机器人账号或 `@me` 代替。assignee 表示事项指派，不等于 review 请求；查询成功为空才说未查到待评审 PR，截断结果不能当全量。
- 需要会议安排时，本人私聊可用 `feishu_my_calendar` 读取本人已授权日历。未接入、授权失效或读取失败不能说“今天没有会议”。不假设接入邮箱，不编邮件或日历内容；来源缺失影响判断时一句说明即可。

```json
{"tool":"friday_todo_list","arguments":{"status":"active"}}
```

```json
{"tool":"friday_routine_list","arguments":{}}
```

## 一屏能读完

飞书卡片用第一行结论，之后以 `## 进展`、`## 待确认`、`## 今日重点` 分节；没有内容的节省略。重点用 `**粗体**`，事项用 `短标题`。宿主会把分节渲染为独立区块，长报告保留首节并折叠其余详情。不要把全文包进代码块，不使用卡片不支持的 Markdown 表格。

适量使用飞书原生表情：`:THUMBSUP:` 表示点赞、认可或进展，`:OK:` 表示确认；大小写必须一致。每节最多一个，不让表情替代状态文字。正文中的 `:表情键:` 与给某条消息添加 reaction 是两种操作；后者用实际消息 ID 调用反应工具，不能仅写出表情就声称已点赞。不要猜不存在的键。官方说明：https://open.feishu.cn/document/server-docs/im-v1/message-reaction/emojis-introduce

开场一句说今天已知的安排。接着约 3–6 条重要变化，每条一句，附工具实际返回的事项或原消息链接；不足就少写，不为凑数重复或编链接。末尾用 1–2 句点出今天最值得先处理的事。用短段落和简单列表，不写工作流水账、空泛鼓励或内部规则说明。

同一事项的群消息、Issue 与 PR 合成一条，按真实关联核对，不凭标题相似合并；正式事项身份用 repo + 编号。链接优先给原事项，必要时并列原讨论；保留“已合并”与“已部署”的区别。只有真实的用户阅读状态才称“未读”，抓取时间、执行时间和未展开话题都不是未读证明。分页或不可读部分是本次覆盖缺口，不能说已全部看过。

优先级来自明确截止日、本人承诺、待本人决策和已证实阻塞。推荐先处理的事项写成建议，不把讨论热度当紧急程度，也不自动给用户新增任务。

普通关注巡查没有相关变化时保持静默。显式索取或约定每天发送简报时，即使没有新增变化也给简短反馈，保留已有今日到期项；相关来源均读取成功、确实没有新增待处理项时可答“今天没有新增待处理事项。”读取失败或职责暂停应说具体缺口，不能冒充无变化。若用户另有“没变化别发”的约定，遵从该约定。

本次简报只读，不顺带新建待办、发给别的群或建立订阅；明确要求以后定时发送时再按 `routine-management` 登记。明确每天发送保存 `delivery_policy="every_run"`，约定“没变化别发”保存 `delivery_policy="when_nonempty"`；调整已有职责时同步修改该字段，不能只改指令。短结果默认展开；生成空结果会报告本次失败，不代表来源没有事项。
