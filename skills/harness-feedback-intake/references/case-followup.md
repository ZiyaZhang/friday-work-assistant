# 续接案件，不重新收一遍表单

只有记录/维护委托成立时才写案件；只读提问不顺手登记。以下为调用形状示例，ID、原文和消息 ID 必须来自本次真实上下文，不能照抄示例值。

已有案件先读取阶段、缺口、原反馈和证据引用；已明确案件编号就不再要求用户重复描述。

```json
{"tool":"friday_bug_context","arguments":{"id":12}}
```

新反馈先用 `friday_bug_similar` 按现象查本域候选，再用 `friday_bug_record` 存原话。记录当前发言时省略 `message_id`，宿主绑定当前真实消息与发言人；记录已读取的历史反馈才传它的真实 ID。只有现象、触发和版本支持同案时才带候选 `bucket_id`；标题相似不是合并依据，一条消息不能被强行改归其他案件。

等待信息只记影响当前判断的缺口。向用户一次只问最有用的一项；已经回答的问题不再追问。用户原话里明确说不提供或拿不到的材料（会话日志、截图、复现步骤、版本），登记时用 `friday_bug_record` 的 `declined_info` 记下，之后才说的用 `friday_bug_intake` 的 `declined_info` 追加；补问答复处理为 `declined`/`unavailable` 时，宿主按该问题的 `info_kind` 自动记入。宿主会拒绝重复索要这些材料：`friday_bug_ask` 遇到 409 就照实转告“这项你之前说过不方便给，我不再要了”，按现有信息继续，不换一种说法再问。用户之后主动发来的同类材料照常读取和核对。

`friday_bug_intake` 只更新阶段，不发消息；`message_sent=false` 是本次操作的事实。`open_question` 非空时先处理已有问题和答复。不要先把三个缺口写进最终长文、再当作已经完成补问。

已有案件需要信息性补充时，用 `friday_bug_ask` 发送问题，传本案 ID、`kind=info`、所要材料的 `info_kind`、一句具体问题和缺失项。工具已经发送，最终回复只说新增发现，不重复问一次；没有独立核查可做就结束本轮。决策审批不走这个工具，不能把未回答或超时当作同意。

例如用户说“先查着，日志晚点给”，可以问“出问题前最后一次操作是什么？”，同时继续已获授权、不依赖日志的核查。有日志就在当前附件中分析，不先要求 Session ID。只有普通答疑委托时，直接在对话里问必要问题，不为使用此工具另建案件。

需要排查时，先把用户可见现象与实际代码对应起来；界面上还留着内容，不足以确定内部处理到了哪一步。涉及具体请求或处理阶段的解释和补问，先核验实现与证据。回执按本次委托确认实际动作，有新发现或必要问题才补充；详细代码依据留在案件或应用户要求展开。

明确回复问题消息后，宿主会带入 `question_id`、`current_reply_id` 和真实答复。读 `friday_bug_context` 后，用 `friday_bug_reply` 记录本条答复：`answered` 是提供信息，`declined` 是不愿提供，`unavailable` 是拿不到。后两种仍可按现有材料继续；缺口没有因此补齐，也不授权建单。后来主动上传的材料照常核对，保留先前答复。

发送状态 `sent/confirmed` 才能说已发出；`unknown` 保留待核对，不能换一种问法重发。遇到来源或权限拒绝，简短说明实际缺什么，不把工具内部限制抄给用户。

```json
{"tool":"friday_bug_intake","arguments":{"id":12,"phase":"awaiting_info","missing_info":["卡住前最后一次操作"]}}
```

证据足以进行本次核查时显式清空必要缺失项；ready 表示可以进行所述核查，不表示日志完整或已经复现。仅源码分析也可以 ready，但 note 要注明范围。

```json
{"tool":"friday_bug_intake","arguments":{"id":12,"phase":"ready","missing_info":[],"note":"已有最小复现，先核查代码；尚未接收原始日志"}}
```

原消息用专用入口关联，网关验证当前会话与话题；它保存的是引用，不会下载或分析附件。当前 MCP 不能手工登记 user_export/feedback_receipt 为已收取证据，不拼造上传回执。已有引用 expired、unknown 或 partial 时保留缺口，不能据此宣布完整/无错误。

```json
{"tool":"friday_bug_evidence","arguments":{"id":12,"message_id":"om_example"}}
```

`formal_status_source=github` 的案件回读关联 Issue。不能继续用本地 intake/fixed 覆盖正式状态；需要新增事实时先读原 Issue，在明确发布授权下补评论。用户不再补信息时按现有证据说明未验证项，不因此自动建单或催人。

确需之后回来检查且在委托范围内时，转 `routine-management`，登记真实事项、检查时间、原话题和完成条件；取得成功回执后才能说已安排，定时检查不称实时监听。用户打不开链接与工具能否读取是两件事：404 本身不证明私有仓库或事项不存在；回执直接说明用户获准知道的结果，不让链接成为唯一交付。关闭或合并不等于发布，只有核实修复进入相应发布版本后才告知版本号；登记失败或版本未核实时，不承诺“发布后自动通知”。
