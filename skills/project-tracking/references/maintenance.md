# 只在对应委托成立时维护

## 仓库范围与表格看板

`friday_project_repositories` 不传参数只读本空间范围；只有**部署管理员**在明确要求配置时才传 `repos`，这是替换整个列表，追加前先读取并保留现有授权，撤销可传空数组。空间负责人不自动等于部署管理员。授权不能继承到别的空间，换群后重新授权；普通进度查询不要改配置。

```json
{"tool":"friday_project_repositories","arguments":{}}
```

旧飞书表格看板用 `friday_pmo_board`：不带 args 只看本群状态和链接；明确要求同步且本群负责人有权时才 `args="sync"`。它是本群临时事项表，不是 GitHub 项目镜像或中央跨群 PMO；表格链接本身不授予回写权。当前没有任意表回写或全公司项目授权工具。

## 临时待办和正式事项

先 `friday_todo_list` 定位已有临时事项与来源；用户明确要求维护或已有职责覆盖才写。明确承诺用 confirmed，推断用 candidate；负责人、日期不明就留空。deadline/freeze/release/meeting 需要明确时间，没有时只补时间，不编造排期。

`friday_todo_update` 更新已定位的本地事项：阻塞要带 `status_note`；改期说明原日期与新日期；推断先报告候选，不覆盖确认事实。`friday_todo_done` 只标记已确认完成的临时待办。“合并”“发布”“验收通过”分别保留证据，不能相互替代。当前工具没有 expectedVersion；读回发现冲突先核对，不反复覆盖。

GitHub 正式事项先 `github_get_issue` 读回；明确要求发布进展时才 `github_comment_issue`，通过现有网关确认。没有通用 Issue 字段编辑工具，不声称已改 assignee/status；已有 Issue 不另建待办充当完成状态。

## 持续跟进项目

明确要求周期跟进、改频率或停止时，按需读 `routine-management`；那里说明登记、更新和停止的实际工具与边界。项目跟进指令应保留本空间已授权 repo、事项范围、时间口径、产出受众和无变化时的静默条件，不能把一次查询自动变成订阅。

已有安排先定位编号并读取原指令，保留用户没要求改的范围；不要删除后重建。读取完整配置的调用形状：

```json
{"tool":"friday_routine_list","arguments":{"id":8}}
```

任务以后执行时还要重新核对权限、同步时间和覆盖；今天读到的项目快照不保证以后仍可公开。不能给一次无更新推导延期，也不能以“代码已合”替代后续的发布/验收确认。
