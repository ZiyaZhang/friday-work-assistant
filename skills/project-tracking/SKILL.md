# 对照事项与证据跟进项目

沿用当前已知项目、时间范围和负责人；只问会影响检索结果的缺口。问总览不先要求用户提供每个 Issue；已有明确编号/链接就直接核对该事项，不先扫所有仓库。

项目总览先用 `friday_project_view`，只展示本空间已授权仓库。问最新、今天或要确认变化时用 `refresh=true`；只看已有快照可不刷新。`repo` 是 owner/name，`assignee` 必须是真实 GitHub login，**这里不解析 `me` 或中文姓名**；当前上下文没有可信映射时只补这个身份信息，不猜。按状态/时间筛选返回项目，说明筛选范围。

```json
{"tool":"friday_project_view","arguments":{"refresh":true}}
```

读取结果时保留 `syncAt`、`coverageComplete`、`stale` 和逐仓库/逐项缺口。未配置说明需部署管理员给本空间授权；拒绝/撤权不能改用全局 GitHub 身份扫库。空结果只表示当前授权范围、筛选和快照下没有匹配，不表示没人工作。当前返回结构没有历史差分，若无前次证据就不能编“本周新增/完成了几项”。

正式事项身份是 repo + Issue/PR 编号；`github_get_issue` 读取明确事项详情，`github_list_issues` 查询时显式指定本次获准 repo、需要的状态（默认只有 open）。GitHub 是正式状态来源，closed PR 不一定 merged。负责人只取真实 assignee，未知就待确认；创建至关闭/合并是日历历时，不是人工工时或指派至关闭。消息量和无更新不能推导忙闲、阻塞或延期。

需要聊天补充时只读相关获准话题，按需展开 thread，区分事实、风险判断和未确认信息。首屏给最需要关注的变化/事项、依据时间及下一步；只读问答不顺手新建待办、记忆、定时任务或同步表格。

明确要求维护、授权仓库、看表格看板或安排后续时，再读 [事项维护与持续跟进](references/maintenance.md)。私人/临时 todo 与旧群表格保留各自出处，不给已关联 GitHub 的正式事项再维护一份平行状态。

有人在群里问到停滞的 Issue/PR（很久没动、一直等 review、关闭了却没合并）时，先用 `github_get_issue` 读详情和讨论，找出直接参与者：作者、assignee、被请求 review 的人、最近在讨论里回复过的人。逐个用 `friday_whois` 查：结果是 resolved 的照返回的写法原样 @，其余只写名字，不猜人。在原话题提一个具体、对方能直接回答的问题（例如「#123 还在等谁的 review？」「这个 PR 关掉是不再需要了吗？」），不泛泛催促。回复前看本话题近期消息：同一事项已经提醒过同一批人、之后没有新进展，就不再 @；没有新信息时只回答提问的人。
