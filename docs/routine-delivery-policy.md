# 每日简报的发送约定

复用现有职责、occurrence 和投递账本，新增一个持久字段 `deliveryPolicy`；API/MCP 输入使用 `delivery_policy`。

| 值 | 行为 |
|---|---|
| `when_nonempty` | 默认值。有内容才发，正常结束且返回空内容或 NOTHING 时记 skipped。 |
| `every_run` | 用户明确约定每次发送。没有新增事项也应简短反馈已核实的情况；模型返回空内容或 NOTHING 则发送一次失败提示，记 failed。 |

旧职责默认保留 `when_nonempty`，不从中文名称或 prompt 猜测迁移。新建、提案、修改、列表和聊天查询使用同一字段；修改字段递增配置版本，保留编号和读取游标。followup 仍回到原话题执行，不接受此字段修改。

失败提示包含职责名称和 `/routine run <编号>`，沿用本次 execution 的 delivery key。提示之前保存失败标记；收到真实 ACK 后即使进程重启，重读同一执行也不会当成成功简报或再次发送。unknown 不换新 key 自动重发。明确重试产生新的执行；连续失败仍按现有规则暂停。

`every_run` 不是绕过授权、完整读取和取消的发送保证。watch 必须读全配置的消息窗口，才可进入生成结果判断；空结果的失败提示不消费消息游标，也不写成功覆盖证明。来源失败或未读全不能解释成“今天没有事项”。当前这一字段不统一其他运行错误的通知路径。

正常短摘要默认展开，较长摘要沿用现有折叠阈值。聊天常规答疑仍只发送最终结果；不新增过程卡，也不以撤回表示完成或取消。

每日简报格式由 `group-digest/references/daily-brief.md` 按需提供：今日安排、约 3–6 条重要变化、1–2 句优先事项。来源链接、去重与缺失说明按真实读取结果生成，不编造日程或未读状态；单次索取不自动建立订阅。

回归覆盖 Store 迁移、真实 HTTP/MCP 的字段读写与提案执行门禁、空结果和失败重入、未知发送、watch 覆盖和短卡展开。测试使用合成飞书及模型，不等同于真实简报质量和长期运行验收。

## 触发阈值、跨输出判重、重叠职责（P4-2）

**阈值（G7）。** 关注职责多两个持久字段：`min_new_messages`（默认 0 = 不设阈值）、`always_on_mention`（默认 1）；API/MCP 同名参数，只对 watch 有效，改动递增配置版本、不动读取游标。调度触发时，网关先用与模型相同的身份（群里建的 = 机器人；私聊建的 = 委托人的 token）经同一个消息服务数一遍读取窗口 `[message_cursor_sec 或 created_at, now)` 里别人发的消息：每个群都读全且条数不到阈值、又没有 @ 委托人或机器人的消息（或 `always_on_mention=0`），就把这次 occurrence 记成 `skipped`（`error='below_threshold'`）、不开模型会话、不发送，**不推进读取游标**：这些消息留到下一轮和新消息一起计数（“攒一批再处理”），够数运行之后才由完整读取覆盖推进游标；每小时 3 条的群到第二轮就有 6 条。达到阈值、被 @、手动触发（`/routine run`、手动执行）、读不全或读取失败时照常运行；prompt 里写明阈值与本次数到的条数。“有重要变化再说（至少 5 条新消息）”“攒一批再处理”由模型填成条数。

**已单独提醒（G8）。** 新表 `reported_refs(owner_open_id, ref, output_key, delivered_at)`，主键三列，只登记四种稳定编号：`todo:<id>`、`inbox:<id>`、`msg:<message_id>`、`gh:<owner/repo>#<n>`（仓库名小写）。登记点都在投递 ACK 之后：待办提醒（收件人 = `owner_open_id`，`todo:<id>`）、Issue 有效性通知（绑定人，`gh:…`）、职责简报（`run_as`，从简报正文里取显式写出的编号，例如工具返回的 `[todo:12]`、`org/repo#7`、GitHub 链接；裸的 `#12` 不算）；投递失败或结果未知不登记；不做文本相似度。简报的 prompt 附上 `run_as` 近 24 小时已单独提醒过的编号（不含这条职责自己以前的简报），要求模型在该条末尾标注「已单独提醒」而不是删掉。

**重叠职责（G9）。** `RoutineStore.overlaps(id)`：同一空间里正在生效的 schedule / watch，「关注同一组群」或「投递给同一受众且写入同一归档目标」（`archive=doc` 的文档按职责各一份，所以只有直接发聊天 / 私聊的会重合），且下次运行时间相差 ≤45 分钟。新建、修改（配置版本变了）、提案被接受后由 `RoutineApplication.noteOverlaps` 给这次操作的人（没有就是职责负责人）登记一条 Inbox 待决定「「A」和「B」产出重复，保留还是暂停其中一个？」；一对职责按 `decisionRef(space, routine-overlap:<a>:<b>)` 只登记一次。人的决定走现有待拍板结清：note 写「保留两条」（或 `dropped`）、「暂停 #编号」或「暂停「名字」」，选了暂停就在同一事务里复用现有暂停；结论对不上三项之一时返回 `needs_choice`，什么都不写。其中一条被暂停或删除后，这对的待决定按领域结清。不自动去重。

## 待办来源覆盖

简报查询 `friday_todo_list` 默认使用 `active`（open/blocked/review）；显式 open 只返回进行中事项。API 保留原 todos 数组，增加同 scope/status/kind 筛选的 total、truncated、limit；MCP 可请求 1–100 条并说明已展示数量。列表和总数共用筛选，不计入其他空间或其他人的私聊。

保留既有排序，超过上限时按状态或类型收窄；仍超出就说明覆盖缺口。这是有限列表的准确语义，不承诺已分页读完，也不把前 30 条没有到期项说成今天没有待办。
