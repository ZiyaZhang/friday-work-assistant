# Friday 目标架构与迁移契约

本文是设计入口，按八层信息流组织。

**重构尚未完成。** 工作生命周期、独立动作核对、学习消费进度和全部入口的统一应用操作仍未闭合。本文的目标接口不等于实现完成。

**先搭好架构，再逐项打磨功能。** 先确定各模块的输入输出、状态权威、事务和恢复契约，并替换实际调用路径；这一阶段只做必要的兼容、停止、权限、重复动作及旧库验证。之后按原 57 项做自然语言、真实模型、飞书和界面验收。具体搭建顺序见架构实施顺序；既有功能编号与失败证据保留。产品参考不等于实现证据，能力和运行机制应以 Friday 源码及验收记录为准。

## 1. 已确定的决定

1. 保留单网关进程、SQLite、DSH ACP 和 GitHub 研发状态源。八层是代码职责边界，不是八个服务。
2. 自然语言是主入口。命令、卡片和人类后台调用同一应用操作；操作结果来自存储与平台回执。
3. Space 是长期工作范围；飞书聊天是绑定入口。逻辑工作线、一次 Run、DSH 会话句柄分别管理。
4. 同一事项继续上下文，独立事项分开。询问进度只查询；停止指定工作，不靠中断整个私聊解决路由。
5. 不另造研发工单平台。图中的 Entity 对应已有的具体领域对象；Ticket 先由案件、补问、工作关联和 GitHub 引用共同提供。
6. 用户已确认：关注群资料可以沉淀为个人长期记忆，必须保留来源；来源授权失效后停用相关记忆。此规则也适用于派生摘要和待办正文，不能通过复制到另一张表失去来源约束。
7. 模型理解、查证、生成候选；宿主负责身份、状态转换、停止、权限、幂等和实际发送。Skill 不实现这些边界。
8. 普通交付不发思考过程或工具流水账，不靠撤回过程卡收尾。信息性补问、授权和决策卡可以立即发送。

默认工程选择：先独立授权消费群历史；不共享用户授权。长任务等待时释放模型执行名额。模型切换不能重做已发生的外部写入。暂不引入消息总线、通用工作流引擎、向量数据库或角色群。

## 2. 信息流与依赖

~~~text
群/私聊/卡片  授权历史  定时触发  后台操作  GitHub 事件/外部回信
                ↓
1 Adapters → 2 IngressStore → 3 Space / IdentityResolver
                                     ↓
       明确请求 / 主动窗口判断 / 职责与学习的独立调度
                                     ↓
                  4 WorkCoordinator / RunScheduler
                   领域对象 + 工作关联 + 等待信息
                                     ↓
                         5 ContextBuilder
                                     ↓
              6 RuntimeAdapter → ToolGateway → 具体连接器/执行器
                                     ↓
                 7 实际动作收据 / 领域变更 / 产物
                                     ↓
                         8 DeliveryService
                       当前话题 / 获准目的地

已接收事件 + 实际动作结果 + 用户纠正
                ↓
独立学习 occurrence → 候选 → 校验/必要确认 → 生效版本
                ↓
后续 ContextBuilder / 职责调度
~~~

编号表达信息流，不强制单向逐层调用。例如模型发送一个必要问题会在 Run 期间经 ToolGateway 调用 DeliveryService。代码依赖保持：入口适配器 → 应用操作 → 领域服务；领域服务通过具体端口调用平台，不能反向调用 Orchestrator。

Orchestrator 最终只负责装配依赖、接收入口、提交工作和关闭服务。不在其中拼上下文、改业务表、解释 OAuth 完成语义、构造 GitHub 回执或决定空间迁移。

八层同时遵守四条契约：**工作链**管理委托与等待，**信息链**管理来源、版本与依赖，**动作链**管理实际外部效果，**授权链**管理当前身份、范围与受众。它们通过持久引用连接，不再各建一套相同状态。

模块按替换需要落文件，不一次搬动整个目录：

| 边界 | 文件落点与约束 |
| --- | --- |
| 入站持久化 | 新 ingress-store.ts 配合现有 ingress.ts；现有 inbox.ts 是个人提案收件箱，不能拿来混存平台事件 |
| 工作/执行应用操作 | 薄 run-service.ts 调用 Registry、Queue/Gate 和具体领域服务；进程内运行句柄不成为持久真相 |
| 上下文 | context-builder.ts 读取已获准的当前材料，prompt.ts 只负责表达；不直接发送、改案件或选择发布受众 |
| 空间与授权生命周期 | 扩展 space-lifecycle.ts；OAuth 完成、空间配置、职责恢复从入口回调中抽成单一应用操作 |
| 运行时与动作 | acp/runtime.ts 与 internal/api.ts 逐步转调具体应用服务；GitHub、飞书继续保留领域适配器 |
| 交付与学习 | 复用 delivery.ts / tool-delivery.ts；学习处理器独立调度、复用 memory/routines，不在回复收尾中做任意写入 |

不生成无调用者的接口层；每次抽取必须替换一个实际调用路径。对外 API 可兼容，内部旧实现应随替换删除。

## 3. 对象、权威来源与现有存储

| 对象 | 权威内容 | 现有载体 / 迁移方式 |
| --- | --- | --- |
| Space | 配置、成员、当前入口、生效版本、停用状态 | 保留 space_rooms / space_members，补配置、权限和绑定版本 |
| InboundEvent | 平台事件、真实作者、回复关系、修订及接入处理结果 | messages、task_receipts、ingress_routes 已承担部分职责；归一入口记录后逐步收敛去重责任 |
| WorkKey / WorkContext | 一段可以独立继续、等待或停止的执行委托 | WorkKey 是稳定身份，薄 WorkContext 管生命周期、授权引用与输入消费进度。沿用 B2 的原 Task 根及可信补充链，不复制案件或 GitHub 状态；当前仅稳定根关联已实现 |
| WorkRef | 当前工作的稳定领域引用及关联原话题 | 使用带类型的原请求 taskId、feedbackId、routineId、GitHub repo/number；sessionKey 和消息别名只是定位索引，不能作为业务权威 ID |
| FeedbackCase | 用户原述、诊断阶段、缺失信息、证据与外部关联 | 保留 bug_buckets、反馈证据与问题表；不存一份可随意修改的 GitHub 状态 |
| Run | 一次执行的触发、开始/结束、取消与结果 | B2 薄 run_attempts 记录 taskId 或稳定职责执行键、workKey、主体和终态；tasks 保留入站原文与补充链，不直接改名 |
| RuntimeSession | DSH 句柄和上下文连续性 | 保留 Registry 对 ACP 句柄的管理；工作线不因句柄失效而消失 |
| Responsibility / Occurrence | 长期委托 / 某次应执行窗口 | 保留 routines、routine_occurrences，各消费独立游标 |
| Question / Reply | 要补什么、回答者、实际答复、拒绝与等待 | 保留现有问题与答复记录；增加 decision 时与审批明确区分 |
| UserTodo | 本人待办、确认状态、来源 | 保留 todos；不是 GitHub Issue 的第二套研发状态 |
| Memory | 生效知识、候选、替代关系、来源 | 保留 memory_notes，补派生来源与生效版本 |
| Action / Delivery | 外部操作意图与实际结果 / 特定受众的投递 | 保留 deliveries、GitHub 创建和追加账本；具体适配器共享恢复契约，不硬合并所有表 |
| ProjectView | 仓库集合和获准来源的只读项目视图 | GitHub 镜像 + 空间/联盟授权；不新增手工维护的项目事项状态 |

工作线可以关联多个反馈或外部对象，一条消息也可能包含两个独立需求。不能用“一条消息只能对应一个案件”的唯一约束抹掉第二个需求。新增关联表只保存映射，不新增平行业务状态。原请求使用不变的 Task ID，补充关系保留原请求链；反馈使用案件 ID。Session 退休或别名改指不改变这些引用。跨会话重新接续由领域 resolver 核对当前授权后定位资料和修改目录，不沿用旧 Session 的权限。

没有待续工作的一次答疑无需建反馈案件。一个 Run 可以读取多个对象；停止接口明确区分 stop_run、stop_feedback_followup、pause_responsibility。停止案件只暂停其绑定跟进，不能因为共享 Session 或 Run 而取消不相关案件。共享活动执行无法局部停止时，保留现有 shared_active_task 拒绝结果和原状态，明确范围冲突，不能宣称该案已停；只有每个动作都能可信归属案件后，才另行设计局部停止。

旧记录中没有确定关联的 followup 保留并列出待核对范围，不声称“所有跟进已停止”。停止后的迟到补充可以存为用户原文，但不恢复执行委托、问题或职责。

### 四项跨模块运行契约

以下是新附件评审后确定的目标约束；除后文明确收窄的 B1 外，尚未完整实现。

**工作与执行。** WorkKey 管理 Friday 是否仍应继续这段委托，WorkRef 关联案件、Issue/PR、职责等领域事实。一条普通请求以原 Task ID 为工作根；真实 `task_amendments` 和精确 Question/Reply 接续继承该根，不按相同 Session、相似标题或相同案件推断。独立需求得到独立委托；只存原话的 `user_note` 不能成为执行种子。一个可写 Run 只领取一个可独立取消的委托，可以读取多个对象。现有共享 Task 先保留诚实拒绝，不宣称已实现局部停止。

薄 WorkContext 的生命周期为 `open / completed / cancelled`；暂停原因单独保存为集合，恢复某项授权只解除相应原因。`running / queued / waiting` 是由当前 Run、派发记录和等待条件推导的查询状态，不另存一个需要模型维护的副本。附属字段至少包含 `workKey、authorityRef、revision、controlEpoch、inputSeq、handledSeq` 及锚点；序号只在该工作内递增，控制变更递增 epoch，使旧准入失效。当前 TaskWork 尚未提供这些生命周期字段。落地沿用原 Task 根，不预设通用工单表。`cancelled/steered` 的旧 Task 是一次输入的执行结果，不等于整个工作永久停止；RuntimeSession 更换也不新建委托。新 Run 引用 workKey、触发 Task/occurrence 和新的 attempt ID，旧 Run 终态不复活。

等待条件属于工作，Run 可以以 waiting 结束。答复入库、授权完成和 Run 准备等待时都检查同一条件：在短事务中核对委托仍有效，保存领域变化及唯一的待续记录；提交后才唤醒队列。依据是当前条件已满足，而不是是否恰好收到过一次事件。info 回复可复用已创建的 queued Task 作为待续记录，不另建平行回复任务。启动扫描和运行收尾扫描同一批持久待续项；多个唤醒只能领取一次。decision、通用等待条件和跨入口恢复仍需后续实现，不能把现有 info 回复队列说成全部完成。

每个等待条件有独立 generation 和明确满足依据；同代只消费一次，重新提问或更改条件产生新代。保存等待之前已经入库的快速答复，必须参与同一次条件检查；不能要求再答一次。保存补充/答复、更新领域事实、登记待续项在同一短事务，网络读取与模型执行在事务外。超时只改变等待原因，不产生授权。

**真实上下文。** A1 PreparedContext 只证明本轮装入的正文和回执一致。实际可见来源还包括旧 ACP 历史及压缩摘要、本轮工具返回、可读目录/缓存/产物和运行时预载材料。后续 Manifest 必须保守合并这些来源，记录运行时上下文代次及材料版本；覆盖不明则不能宣称完整，更不能让模型自报“没使用”解除限制。

失权、忘记或纠正使旧执行上下文失效时，既关闭旧 RuntimeSession，也重新构建可见材料。最小可行做法是新建目录，只重新挂载仍获准、版本有效的材料；原目录留受限审计，不能直接给新会话再次读取。实际工具读取可登记、外部写入可在发生前准入、失效 Run 无法新发受管动作，必须用当前 DSH 实测；ACP 接入本身不是所有原生文件、shell、网络和子进程受控的证明。缺少这些能力时，关闭相应能力或明确限制场景。目录拆分仍不是 OS 隔离。

内部诊断和对外发布可以使用同一 WorkKey 的不同 Run，但发布 Run 只装获准向目标受众披露的材料；不能通过重启清空来源并集后复用旧产物。这是有来源依据的上下文重建，不是把原工作另起一遍。

**动作执行。** Action 的业务身份由领域确定，例如 `issue:create:feedbackId`、`pr:append:repo/pr:patchArtifactId`、`digest:occurrenceId:main`。WorkKey 记录谁发起和如何接续，不应成为同一外部效果的唯一去重范围；两个工作关联同案时仍须找到原动作。Run ID、工具序号和正文 hash 都不是业务身份，payload digest 仅检验内容是否改变。具体连接器沿用现有表，补稳定身份与旧键映射，不先造通用动作平台。后续 Run 先查询原动作；同一操作 unknown 时不能换正文、Run 或 ID 重发，只阻止冲突动作，不锁住整个仓库。新增意图必须明确指向新的操作，不能暗中清除旧 unknown。迁移保留旧 key/回执的映射，不能通过重新生成键绕开历史未决结果。

准入点位于最后一次身份/委托/来源/目标版本复验后、实际外部请求前：短事务把确定未发的 prepared 改为已准入状态，保存请求摘要、意图版本及原目的地；提交后立刻调用适配器，不再经过模型规划。停止先持久使新准入失败；已经准入但无法证明请求未发的动作保留 unknown 并核对，不能承诺撤回。若适配器能证明 token 或校验失败发生于请求启动前，保留可重试的未发事实，不误记永久 unknown。数据库事务与远端 HTTP 之间不是原子操作。

只读 `reconcileAction` 在当前查看权限下更新原收据，不依赖旧 Run 活跃，不扩大写权限。B1 不自动重放已开始的任务，因此先保留现有账本和人工核对边界；在开放已开始工作自动接续前，必须接通跨 Run 身份和具体动作核对，不能等完整后台建成后补。

**信息变更传播。** 来源关系回答“依据哪些材料”，依赖关系回答“该材料变化后哪些待执行对象需要重验”。先在现有对象之间保存窄关联：确认知识版本→todo 指派/截止时间、职责配置→occurrence、领域版本→尚未发送产物；不建立通用知识图谱。明确“把待办改到周五”直接调用 todo/职责应用操作，事务内更新对象并取消或重排相应未执行提醒，不先写 Memory 等模型再解释。聊天推断先候选，确认后才触发依赖重验。

变更与待处理的失效/重验记录同事务提交；各消费者独立游标。已发生的消息、commit 和 PR 不自动撤销，尚未发送的产物在准入前核对依赖版本，过期则重新生成或作废。后台与简报读取需显示相关消费者处理到何处：数据库当前空不等于今天的材料已处理完，读取成功也不能掩盖提炼滞后。

## 4. 应用接口：不同入口共用同一操作

以下是目标接口说明，随迁移进入对应模块，不预先生成一批没有调用者的空接口。

~~~ts
submit(eventId): Promise<RouteReceipt>
queryWork(actor, workRef): WorkView
controlWork(actor, workRef, action, expectedRevision): ControlReceipt
configureSpace(actor, spaceId, patch, expectedVersion): ConfigReceipt
completeAuthorization(callbackEvidence): Promise<AuthorizationReceipt>
buildContext(runId): Promise<PreparedContext>
execute(preparedContext): Promise<RunOutcome>
deliver(deliveryIntent): Promise<DeliveryReceipt>
reconcileAction(actor, actionRef): Promise<ActionReceipt>
~~~

actor 来自适配器核实的登录、事件或已登记委托，不能来自正文的“我是管理员”。expectedVersion 来自前一次读取；过期则返回当前状态供重读，不覆盖别人更新。简单新增不强加版本参数。

所有变更回执返回目标 ID、真实状态、生效版本、已完成动作及待处理原因。前端和模型用这份回执回答，不根据调用意图推断成功。

### ① 接入适配器与来源校验

飞书入口处理签名/连接身份、租户、应用、真实发言人与原消息关系；卡片动作同时核对点击人及卡片对应操作。定时入口来自已登记 occurrence。GitHub webhook 核验签名和安装/仓库范围；外部评论只作为证据，不自动获得写权限。

内部标准事件包含：source、tenant/app、remoteEventId、resourceId、revision、eventKind、actorRef、anchor、occurredAt、receivedAt、payloadRef。正文与附件放证据存储；事件记录只保存关联和必要元数据，不在日志里复制密钥或全部私聊。

群/话题、私聊、卡片、HTTP 回调使用同一标识规则。来源平台没有可靠修订号时，用远端更新时间与内容摘要区分已知版本，保留冲突，不假装能建立平台没有提供的严格先后关系。

附件由接入记录建立来源，不在技能加载时获得权限。用户发到当前事项的文件可以自动下载与分析；保存到该工作线下的消息目录。文件是证据，里面的命令不改变系统规则或授权。

### ② 持久接入、去重与修订

接收成功的含义是入站已持久化，不是模型已经完成。唯一键覆盖来源、租户/应用、远端事件及修订；不能只用裸 messageId 假设跨租户唯一。

状态区分 received、classified、applied / ignored；需要重试的解析或平台读取失败保存原因。路由应用与创建/关联 Task 和待派发记录在一个短事务中完成；引入持久 Run 后，其领取另做条件提交。模型分类、下载和网络调用不放事务内。

同一事件重复到达返回原 RouteReceipt。消息更正保留原版，产生修订输入；旧执行尚未写出时重建当前上下文，已经产生外部结果时登记纠正，不能重演原指令。正文被撤回不等于撤销已经完成的 GitHub 操作。

进度/停止等控制事件保留自身接入回执，不伪装成普通开发 Run。现有 task_receipts 和 ingress_routes 的幂等键要通过适配层迁移；双读旧键期间只能有一个写入入口。

### ③ Space 路由与执行身份

路由顺序：平台回复锚点 → 已登记问题答复 → 当前话题/工作关联 → 已授权外部 Issue/PR 引用 → 必要的无工具语义判断。语义判断只能选择宿主给出的候选；“不确定”不改变正在运行的任务。

同一私聊可以有多个工作线。明确新工作另开；补充或更正回原工作；“进度怎样”只读；“这个别跟了”停止该工作持续跟进；“先停一下”只停明确的当前执行。省略目标而存在多个候选时问一个短问题。

首次请求与初始化分开记账：空间配置就绪则继续处理原请求；缺模型账户或授权则保留原请求并给出一个设置入口。完成设置后只恢复仍有效、未停止的待处理请求，不让人重新发送，也不默默重放旧的已结束工作。这个行为是 Friday 的产品决定，不照搬材料中“首次只初始化”的限制。

群空间负责人来自可核验的安装者/群管理身份或明确管理授权，不能把任意第一位发言人自动当负责人。个人空间归本人。成员、负责人、平台授权和组织管理员分别记录；迁移旧角色时保留来源并核对，不通过姓名匹配合并身份。

执行身份分成：

| 字段 | 谁决定 |
| --- | --- |
| initiator | 真实消息作者 / 人类登录主体 / 触发职责 |
| authorityRef | 本次明确请求、已接受职责或有效审批的持久引用 |
| dataPrincipal | 每次连接器实际采用的个人委托或应用身份 |
| executor | DSH 实例 / 已配对设备 / 受限执行环境 |
| billingPrincipal | 实际模型账户，不等同飞书发言人 |
| audience | 固定的原话题、本人私聊、指定文档或仓库 |

这些是不同职责，不要求每项都有不同账号。当前可能同一人承担多项，但不能用一个 open_id 替代全部语义。

每次工具读取、执行与发布按当前授权重验；Run 的身份快照仅供解释与审计。明确职责内动作直接执行，不逐轮重复确认；超出仓库、受众或动作范围才需要新的决定。

authorityRef 必须落到允许的操作类别、资源、目的地和必要审批参数，不能只指向一段自然语言。操作者有管理空间权限，不意味着“分析日志”的 Run 获得修改配置的委托。控制既有委托的停止/暂停不携带派生正文，继续复用现有控制授权，不借此扩大读取、新建或发布权限。

OAuth 成功必须实际核验主体和新授权，再恢复因此暂停的职责。手动暂停保持暂停；共用凭据过期可能影响多个关注群，回执按实际影响范围生成。

### ④ 工作接续与 Run 调度

队列只负责领取和串行执行。工作、等待信息、职责状态从领域存储读取；不藏在队列闭包或模型记忆里。

同一工作线上可写执行串行，不同工作线按全局容量并行。只读进度不排在长任务后面。多个工作线写同一 PR/文件资源时由该资源的动作服务做版本核对；不能只靠 Session 锁。

Run 目标状态：

| 转换 | 触发及副作用 |
| --- | --- |
| queued → running | 核实空间/委托/版本仍有效，领取模型名额 |
| queued → cancelled | 尚未开始的明确停止，不启动模型 |
| running → completed / failed | 保存实际结果后释放名额；完成与结果投递状态分别展示 |
| running → waiting | 保存等待引用和工作检查点，结束当前模型执行，释放名额 |
| running → cancelling → cancelled | 先持久取消，再终止可控执行；迟到结果只进入原动作账本 |
| running → interrupted | 网关重启且无法恢复该次运行；核对动作后创建接续 Run，不复活旧 Run |
| waiting → 新 Run | 新答复、授权完成或获准的定时检查，保留原等待记录 |

这是目标状态模型。当前 `RunAttempts` 已持久化 runId、workKey、triggerKey、主体、ACP 绑定与终态，并与 Task/职责领取共用短事务；启动会将已运行 attempt 标为 interrupted，不重放。实际状态为 running、stop_requested、completed、failed、cancelled、interrupted，queued 仍在原 Task/dispatch 中。目标 waiting、统一 Work 控制和跨入口条件唤醒尚未实现，不能把持久 Run 等同于完整接续。后续逐步抽取共用的 claim/requestStop/finish，保留原 Task/occurrence 身份。停止不关闭 Issue、不删除职责、不撤销已提交结果。

信息性问题立即投递，当前 Run 继续独立检查；真正需要答案才能继续时进入 waiting。decision 暂停依赖动作，超时和“无法提供”均不是批准。问题 answered 只代表答复处理完，不代表缺口已解决。

当前 occurrence 唯一约束包含 routineId、scheduledAt、configVersion。目标需分开“逻辑执行窗口”与“实际配置版本”：只改长度或模型不产生第二次相同窗口；调度变更明确取消旧待执行窗口并产生新窗口，手动再执行使用独立触发 ID。迁移必须保留已有 occurrence 和 Delivery，不以重算 key 重跑旧窗口。读取、处理和发送分别记录：材料已处理但投递 unknown 时不得重新生成另一份摘要，恢复先核对原 Delivery。此项不在 B1 中顺手改变。

职责暂停原因拆分为手动、授权失效、结果待核对和配置失效，恢复入口只能解除对应原因。相同授权完成事件不能解除其他暂停。

### ⑤ Context Builder

ContextBuilder 从一个持久 Run 和已核实的读取计划构建上下文，不接收模型自报的“我可以读这些”。分三步：确定当前范围 → 读取/裁剪材料 → 同时产出模型输入和上下文清单。

PreparedContext 包含：

| 内容 | 必需事实 |
| --- | --- |
| 请求与锚点 | 原文、真实作者、消息/回复 ID、修订；本次是新工作还是接续 |
| 当前工作 | 案件阶段、已知/缺失信息、拒绝项、Issue/PR 引用、仍在等待的原因 |
| 配置与能力 | 生效配置版本、实际模型选择、绑定技能版本、可调用动作 |
| 对话 | 当前事项相关消息；页范围、遗漏和截断，不能说“都看完了” |
| 记忆 | 当前有效条目及版本/来源；候选不冒充确认事实 |
| 证据 | 获准文件、聊天、代码提交、平台状态；内容与来源一一对应 |
| 交付约定 | 实际受众、产物类型和该类型的表达长度 |

ContextManifest 按 runId 保存版本、引用、实际覆盖、缺口和模型/技能配置，不保存隐藏思考。普通查询只展示读者有权看到的摘要；调试记录同样受来源权限约束。

当前 `RuntimeContexts` 已持久保存 ACP 上下文及每 Run 消费的记忆版本，`SourceContexts` 保存实际来源；`ExecutionSessions` 负责会话准入和重建。候选的受管文件层继续登记内容 digest、代次、原 Run 与来源，并由宿主复验实际读取。它们尚非所有运行模式的完整 Manifest：普通 workspace 的原生文件/Shell 来源覆盖未知；跨代材料重建、派生 todo/计划的完整依赖仍缺。旧 ContextReceipt 与 Session 来源兼容路径仍在，不能直接删除旧限制来“修好”正常写入。

同工作复用 DSH 句柄前比较上下文有效版本。撤权、记忆纠正/忘记、空间停用使已读取旧内容的句柄失效；新句柄只装当前允许的记录。无关工作不继承整段私聊。无法证明某产物只用了局部材料时，其来源继承该次执行可见材料的并集，不能让模型自选较少来源来放行。

来源细化的目的包括：读获授权群后可以生成本人的待办；并不意味着可以把这个待办转发给任何群。

### ⑥ Runtime Adapter、模型选择与工具网关

DSH ACP 继续负责模型循环、工具调度和会话执行。Friday 的 RuntimeAdapter 提供 start/resume、execute、cancel、close、实际使用模型/用量/停止原因；不重新实现 Agent loop。

模型解析输入是配置版本、角色与账户授权，输出是实际 provider/model/account 引用。worker、无工具路由判断、学习可以分别配置。DSH 实际运行能力必须经过适配验证；仅保存配置不算模型切换成功。

备用模型只接续已登记工作的当前状态。纯模型请求失败且尚无副作用时可换；已发生工具动作时先核对账本，再创建新 attempt 继续。不能从最初 prompt 整体重放。未拿到用量返回 unavailable，不估成零；费用根据实际账户和可验证价格记录，缺价不编金额。

ToolGateway 区分读取、可写操作、发布和控制。无工具路由/接单评估运行没有开发目录和外发工具；不是把 MCP 列表设为空就认为其他原生工具消失。

工具说明只写参数、前置条件、副作用和回执；场景方法进 Skills。每次工具返回引用实际来源和覆盖。自然语言控制操作调用同一应用服务，不制造合成用户消息绕回巨大命令处理器。

### ⑦ 实际结果、领域状态与产物

写动作保存稳定 actionId、授权引用、目标、意图摘要、已核实版本与实际结果。采用具体连接器的状态机，对外保留 prepared / executing / acknowledged / confirmed / failed / unknown / cancelled 的区别，回执另列实际派发、平台 ACK、回读验证和远端 ID。

准入封存具体 payload/产物版本、当前 authority、来源/依赖版本及固定 audience。模型之后改变正文，必须产生明确的新意图并核对原动作；不能复用旧批准替换载荷。各连接器只实现能提供证据的状态；没有回读接口时停在 acknowledged，不为了统一枚举编造 confirmed。

prepared 仅用于能够证明还未发送远端的情况，可在当前授权下继续。现有 Delivery planned 是发送前已经记账但可能随后派发的状态，重启时应按 unknown 处理，不能机械映为 prepared；sent 只映 acknowledged，回读验证满足连接器条件后才 confirmed。executing 宕机后变 unknown，不能当失败新建第二个动作。若平台支持幂等键则复用；否则按远端 ID、内容标记或对象版本读取核对。无法证明未执行时保持 unknown，并提供核对入口。

GitHub：

- 研发状态从平台读取，记录 fetchedAt 和覆盖。合并、发布、用户验证分开。
- 建 Issue 先查重，记录具体新增或追加结果，不能把提及负责人说成已指派。
- 首次 PR 与同 PR 追加提交分别记账；追加基于已确认 head，远端变化则保留本地修改并重新核对。
- PR 评审读取文件、reviews、行内评论及各自分页缺口，核对读取期间 head 是否变化。
- webhook/轮询按平台事件与对象版本去重，只唤醒已登记的关注，不能扩大委托。

产物记录来源、生成 Run、实际文件/平台对象和可访问地址。HTML 写完不等于原型交付；须有可打开地址、真实浏览器检查和截图。上传附件、派生报告和工作目录各自按工作线归属，文件名不是权限依据。

### ⑧ 输出发布与受众校验

DeliveryIntent 固定 action/run、原始目的地及绑定版本、产物来源、稳定投递键和有效载荷摘要。发送前重验当前空间、成员/个人主体、来源与受众；不能在晚到结果里重新取新 chatId 并自动发往换绑群。

所有结果、问题、授权卡、提醒、文档、表格和主动消息逐步接入同一应用交付规则。底层可有不同 API 和账本适配器；不要求文件上传与文档编辑硬套成同一个 HTTP 请求。

主结果已发送但附言失败，只处理附言。投递 unknown 可查询并核对；不能一边显示“已完成”一边永远无可恢复入口。执行完成与送达完成在后台分别展示。

reconcileAction 是独立的只读核对操作。当前有权查看原操作的主体，依据原 actionRef 读取平台实际结果并更新原收据；不要求原 Run 仍 running，不复活它，也没有再次发送权。来源失效时不返回原正文，平台无法证明时仍 unknown。后续继续工作必须由另一个有效委托创建 Run。当前 Delivery.reconcile 仍依赖原运行上下文；必须在开放已开始工作的自动接续前替换这条依赖，不能推迟到后台或 D 阶段结束。**2026-09-21：飞书投递侧已由 `DeliveryReconciliation` 承担（查看者按当前空间与实时成员核验，回读/窗口查找，条件更新原收据），Console 为首个调用者；GitHub 账本的独立核对仍待做。**

普通消息按结果说 1–3 句。每日简报一屏：一句当天安排、约 3–6 条重要变化、末尾优先事项；同一事项合并，保留到期任务与来源。读取失败写实际缺口，不能写“没有事项”。没有约定每日必报且没有变化时保持安静。

## 5. 学习如何生效

学习是独立消费者，拥有来源、授权和游标，不复用巡查/发送游标。读取聊天修订、实际工具结果、用户纠正；失败工具产生的“打算完成”不能转成已完成事实。

| 候选类型 | 生效方式 |
| --- | --- |
| 自动提炼的解释/经验 | candidate，保留原始证据；不覆盖已确认记忆 |
| 用户明确“以后这样答”的本人偏好 | 核实作用域与配置权限后直接通过应用操作生效，返回版本 |
| 用户纠正既有事实 | 定位旧条目，保存来源及替代关系；含糊纠正仅作为候选 |
| 个人 todo | 有明确本人指派依据才标确认；条件句/他人承诺保持候选 |
| 职责、技能、能力扩展提议 | proposed，接受后才生效；过期点击不复活，72 小时只是当前产品默认 |
| GitHub 状态 | 引用平台事实和时间，不转存为可自由编辑的确认记忆 |

候选生成和提交分开。提交在短事务核对对象版本；冲突重读，不能用模型整段覆盖现有笔记。学习消费游标与候选写入一起提交；发送提议卡另走 Delivery，不因通知失败重复产生候选。

记忆来源失效时：先同步阻止相关新读取与外发 → 让已携带相关材料的 RuntimeSession 失效 → 后台把派生内容标为 unavailable。查询过滤在读取时生效，不等待后台标记完。保留受限审计引用，不向失权用户显示原正文或敏感标题；重新授权后核实来源仍存在且范围允许，再恢复使用。明确“忘掉”不因重新授权复活。

跨群长期记忆按已选方案实施。在派生来源与会话失效链路完成之前，不提前扩大自动沉淀范围。

## 6. 飞书、部署环境、GitHub 的落地约束

### 飞书

区分机器人在群、本人可访问、已授权读取、已关注、授权失效和读取失败。用户授权能否读取机器人不在的群，以及历史可见范围，按真实租户接口验收，不在设计里假设 token 万能。

后台人类登录必须独立于 Agent capability。OAuth state 绑定实际发起人、有效期和回调；浏览器会话使用受保护 cookie，变更请求校验 CSRF；每个资源操作再次核对 Space 角色。授权链接是入口，不是资源访问许可证。

空间后台先提供概览、本人任务与职责、知道的事、项目进展、设置与执行记录。生效配置、实际模型/技能版本与最后运行原因都从应用查询获取。模型账户密钥不经聊天展示。

### 部署环境

继续沿用单实例网关与现有部署方式。部署前独立目录构建/回归，停旧实例、备份数据库、迁移、验证健康后记版本。网关健康不等于飞书/模型行为通过。

在内核受限、缺 bwrap/Apptainer 的环境里，同 Unix 用户、分目录、环境变量白名单均不是文件和网络隔离。独立工作目录先解决修改冲突；跨空间不可信代码执行的隔离承诺，要等独立 OS 身份或可验证容器环境提供并完成越界实测。

当前不自研远程调度平台。定义 ExecutorAdapter 的 submit(actionId)、status、cancel 和 artifactRead；实现设备配对、撤销、断线对账时复用动作标识。记录执行环境能力，缺少隔离能力不能静默降级后仍声称已隔离。

外网代理按连接器/命令配置，不全局覆盖；模型连接和代码仓库使用各自实际路由。网关持有平台凭据，模型只拿当前 Run 能力；同时明确同 UID 原生读取仍是未解决的实际边界。

### GitHub 与 PMO

GitHubIdentity 支持安装身份和当前过渡 PAT，回执显示实际身份，不固定写“机器人 App”。配置白名单、当前主体读取/写入/发布范围分别校验。

PMO 默认项目视图：仓库集合、负责人、Issue/PR 状态、明确阻塞、里程碑、关联执行与同步时间。人的视图只引用 assignee 和本人更新；历时与 Agent 运行时间分列，不推断人工工时。只读镜像查询也按查看者权限过滤。

这覆盖研发 PMO，不代表完整通用团队事项系统。培训、供应商和非代码设计交付可后续接入明确的飞书表格或其他权威来源；不能为了填齐界面，把它们伪装成 GitHub 事项或复制成另一份研发状态。

## 7. 生命周期、并发与恢复

| 情形 | 确定行为 |
| --- | --- |
| Space 停用 | 拒绝新工作；停止队列/活动执行和未发结果；职责保留为停用，下一条消息不重建空间 |
| 重新启用 | 明确操作后恢复接入；重验职责授权，不重播旧结果或已过期的一次性提醒 |
| 记忆纠正/忘记 | 生效版本改变；携带旧信息的会话失效；历史事实留痕，但旧正文不再用于后续回答 |
| 取消关注群 | 停未来读取和关联调度/未发通知；历史资料受当时保留与当前授权规则管理 |
| 换绑 | 预览迁移范围 → 校验两边 → 暂停旧接入/外发 → 处理在途 → 提交绑定版本 → 重验职责 → 恢复 |
| 运行期间撤权 | 未发送动作立即拒绝；已发远端动作核对原结果，不向新受众转发 |
| Run 停止但外部结果未决 | Run 可以取消，原 Action 仍是 unknown；核对器只更新原收据，不重新发送或复活工作。核对读取仍需当前有效权限，无权读取则保留待核对原因 |
| 同时改同一业务对象 | 读取版本后条件提交，冲突返回重读；模型调用不占数据库事务 |
| 服务重启 | 只有完整持久交接且能证明从未开始的 queued 可在当前权限下重排；已开始执行记 interrupted、外部未知只对账；waiting 重新检查条件而非仅等下一次事件 |

完整换绑在上述流程实现前继续关闭。默认可带走配置、获准知识和经重验职责；不默认携带旧群原文、私人评价或个人授权。两边已经有空间时不能自动合并；生成预览后明确选择。

不同语义使用不同版本：配置版本决定一次执行用什么配置；授权版本控制当前是否仍可做；绑定版本控制结果去哪里；领域版本控制是否覆盖旧数据。不拿单个 updatedAt 同时替代它们。

旧数据库备份恢复与普通进程重启不同：先冻结外部派发并停止旧网关，标记备份时间后的效果范围待核对，再按远端实际状态恢复收据。未完成核对不开放冲突写入。还原 SQLite 不会撤回备份后已经发送的消息、Issue 或提交；不能把回滚数据库当成回滚外部系统。

沿用现有场景技能，补按需参考和正反例。验证自然语言工具选择、结果正确性、实际副作用和消息外观；不能仅检查提示词中是否出现一句规则。

## 10. 迁移顺序与退出条件

先完成 架构搭建顺序 的模块和实际接线，再按原 57 项打磨功能。以下 A–F 保留既有切片归属，不再要求为每个场景先反复优化模型文案；每条迁移仍立即验证停止、权限、去重和旧库。不能因目标是先搭架构，就只生成空接口或把场景分支继续塞进 Orchestrator。

| 阶段 | 替换范围 | 可验收结果 |
| --- | --- | --- |
| A 统一上下文 | 先抽出 Builder；普通请求/补充共用；随后职责和学习接入同一契约 | 上下文正文与使用清单由同一结果产生，不串入另案；本阶段不宣称重启后已可恢复清单 |
| B 统一工作接续 | B1 先闭合 ingress→原子 Task 交接→从未开始的 queued 恢复；后续补 WorkKey、run_attempts、持久 Manifest 和具体动作核对 | B1 不漏已接收入站、不重放已开始任务；完整 B 再验跨 Run/会话、等待与 GitHub 接续 |
| C 来源与学习生效 | 派生来源、授权失效、记忆版本、Skill 绑定版本和会话重建 | 用户更正/忘记/撤权后，新回答不再使用旧材料；本人待办正常生成 |
| D 应用操作与交付 | 抽空间生命周期、授权完成、职责控制；补齐外部投递和核对入口 | 聊天/卡片/后台同状态，停止可验证，未知结果可恢复 |
| E 人类后台与模型 | 人类登录、五个入口、生效配置、真实模型账户/切换/用量 | 人能看懂、纠正和停止；网页修改实际影响后续 Run |
| F 执行环境与扩展 | 独立身份/容器或设备适配器；完整换绑、MCP接入、原型发布 | 按真实能力验证隔离、断线恢复、迁移范围和可打开产物 |

现有 PR 追加补丁作为 B 的已准备领域能力保留，不为完成它继续扩大临时 Orchestrator 分支。后台、学习和模型设计已在本文约束接口，具体实现评审随阶段提交，不能把“已设计”填成“已实现”。

### B1 最小切片：持久入站交接

复用 `tasks / task_receipts / task_amendments`、Question/Reply 和现有队列。新增或扩展的交接记录只保存：可信入站原文或持久引用、tenant/app/chat/actor、回复锚点、原候选快照、分类结果、绑定 Task、dispatch 的 pending/started/终态及原因，不成为业务事实源。不凭历史裸 queued 行、最新 alias 或“最近一个 Task”补造入站。

1. 接入先持久接收；分类前已有候选必须保存。当 classified 尚未应用时重验原目标状态与当前权限，不能重启后换成最新话题。无法重建旧瞬时 Run 目标则返回状态已变，不应用控制。
2. 一个短事务应用 decision：新工作连同 Session/必要 alias、Task/receipt 一起写入；补充保留精确 amendment；明确答复连同 Question/Reply 一起写入；停止用条件更新。同步写 applied 回执和 pending 交接，失败全部回滚，事务提交后才 abort 或唤醒队列。
3. 重复入站读原交接。合法 pending 可以再次唤醒，不能因为 receipt 已存在就永远跳过；内存队列只是派发手段。领取在外部权限读取之后，再同步核对原绑定、Task queued、stopReason、空间/案件/问题/职责仍有效，并将 started 与 Task running 原子提交；多个唤醒只成功一次。
4. 启动取得现有单网关锁，先按原规则把不确定投递转 unknown，再扫描交接。pending 且从未开始的任务重验后可派发；started/running 保留 interrupted 或待核对，不重放。旧库缺原始交接的 queued/running 不猜测补齐，显式留为未自动恢复。不得把 unknown 的 Task 改成 queued。
5. 已精确绑定的早到答复已是 queued Task，恢复复用同一交接。还未取得真实平台 remote ID 的 `pending_question_replies` 保留原文及待核对原因；不能根据同人、同 Session 或 unknown 投递猜所属问题。完整通用等待/授权/GitHub 唤醒后续另做。
6. B1 保留原投递和 GitHub 操作键，恢复不重发已开始动作。它不宣称已实现持久 Run、跨 Run 动作恢复、全部工具来源追踪或工作目录隔离。

退出用例：分类前/后崩溃；applied 与 Task 写入间故障回滚；提交后派发前崩溃；答复已存但尚未派发；两个唤醒竞争；领取权限 await 期间停止/撤权/归档；旧 started 任务及 unknown 投递不重放；别名改变不串案；旧无交接记录不伪造恢复。用例映射 G35，联动 G32/G34/G24/S14，保护 G07/G33/S06。

每阶段迁移方法：保留当前对外工具/API → 内部转调新应用模块 → 做等价与新增行为回归 → 独立评审 → 独立开发机验证 → 发布 → 自然语言实机检查。单入口切换后删除旧实现，不能长期保留两套配置或状态写入路径。

每个切片上线前都必须同时保持当前停止、授权复验和去重路径，不能把这些保证推迟到 D/F。若新增接续路径没有这三项，就不开放该路径。前台控制保留独立容量；人工请求优先，职责和学习使用有界后台名额。主动介入另需持久窗口决定，并在执行前核对是否已有人工/职责工作接管，不能靠各入口独立正确就假定不会重复。

数据库新增采用可读旧数据的迁移，不改写原外部回执。每片先对一致旧 DB 副本执行迁移和重启回归，核对 quick_check、历史数量/引用、重复迁移幂等，以及 queued/running/unknown/停止记录不被错误复活；测试不得把旧库仅替换成全新 schema。记录所用旧版本、备份与恢复条件，证据不复制凭据和业务原文。涉及不可逆数据变化的版本不承诺直接二进制回滚。

## 11. 贯穿验收

1. 历史检索：请求某人两周前发的资料 → 继续翻更早 → 发原文件/链接；核对真实作者、时间窗、未读部分和附件来源。
2. 反馈到交付：建议带两个限定 → 查重并保留原意 → 信息性补问 → 用户拒绝日志 → 继续代码核查 → 同一 Issue/PR → review 后更新原 PR → 原话题短回执。
3. 私聊并行：两个事项交错，问进度不打断；停止一个、另一个继续；明确回复旧问题回到旧工作。
4. 关注群：授权过期 → 仅暂停实际受影响项 → 授权完成 → 保留手动暂停 → 从检查点接续；期间无假空结果、重复待办或重复报告。
5. 学习：自动候选 → 本人明确纠正 → 生效 → 换新会话仍正确 → 撤来源授权后不能继续引用；恢复授权不复活明确忘记内容。
6. 配置：自然语言、按钮、网页分别修改同一字段；并发旧版本被拒；显示实际模型/技能版本。
7. 投递：远端已成功但本地未记住 → 重启核对；不能重复发、重复建单或假报失败。正文已发而附言失败分别恢复。
8. 简报：连续多日同一事项只报有意义变化，保留到期项；一屏可读，链接正确，缺来源不编排期。
9. 生命周期：运行中停用/撤权/换绑/取消职责；迟到工具结果不能重新开启或改投新受众。
10. 产物和边界：实际打开原型、点交互、窄屏截图；执行环境做越界读取/网络验证。目录不同不算隔离通过。

每个场景保存输入、源版本、实际动作、持久状态和真实回执；模型测试与宿主验证分开。真实平台与 UI 未跑的场景直接标待验，不以测试总数替代。

## 12. 尚待实测的外部事实

- 飞书真实租户可用范围、机器人不在群的委托历史读取、回调地址和用户登录配置。
- 当前 DSH 版本能否按独立 worker 实例切换主备 provider/账户及返回用量；不只核对配置文件。
- 哪个执行环境能提供实际文件与网络隔离；单机部署不满足完整承诺。
- GitHub webhook 可达性、实际安装/PAT 身份与各仓库写权限；现有凭据可读不等于可向任意受众发布。

这些事实不妨碍不改变行为的模块抽取，但分别是“真实来源完整、旧材料失效、全部工具受控、多空间安全执行”等承诺的前提；相应验证未过就不能宣布能力完成。涉及租户授权、设备选择或信息迁移范围的用户决定，再展示具体方案后讨论。
