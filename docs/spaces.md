# 空间：产品的原子单位

> 状态：历史架构决策，分批落地；下文能力状态保留记录当时的判断，不代表当前验收结论。
> 设计目标：空间统一关联配置、记忆、职责、成员和执行记录，既是作用域，也是这些状态的归属边界。

---

## 0. 一句话

空间的读写边界：

> **手和嘴留在本空间，眼睛经授权可以看别处。**

这句话同时说明**能力**和**承诺**：
- 手（做事）和嘴（说话）永远只在当前空间 —— 这是不可协商的
- 眼睛（读）可以伸出去，但**要授权** —— 这是可谈的，且谈的方式是一次显式授权

我们的 Policy 表达的是同一件事（6 动作 × 4 角色），但从没对用户这么讲过。
这句话应该进 `/help`、进欢迎卡、进空间设置页。**能力边界要讲成承诺，不然人不敢用。**

## 1. 我们把空间做小了

现在的空间是第②层里的一个概念：记忆存哪个 scope、权限按哪个空间算、职责挂在哪。
本设计要求空间关联**六样**东西：

| 格子 | 应该有什么 | 我们现在 |
| --- | --- | --- |
| **身份** | 谁是负责人、谁是成员、怎么冻结 | ✅ 有（owner/member，建空间时冻结群主） |
| **配置** | 主模型 + 备用模型 + **主动判断专用模型**、行为偏好、主动参数 | ⚠️ 只有行为偏好和主动参数，**没有模型** |
| **知识** | 「它知道的事」—— 人能翻、能删、能晋升 | ⚠️ 有分层记忆，**没有人能翻的那一页** |
| **职责** | 定时任务 + 提案，统一生命周期 | ⚠️ 职责有，但提案散在两套里 |
| **执行环境** | 这个空间的活在哪台机器上跑 | ❌ 没有这个概念，固定一台开发机 |
| **边界** | 手 / 嘴 / 眼三分，眼睛能伸多远 | ⚠️ Policy 算得出来，但没讲成承诺，**眼睛也伸不出去** |

前三格是补，后三格是**真的要动架构**。

## 2. 两种空间不是同一种东西的两个实例

这是我之前没想清楚的地方。群空间和个人空间在六格里填的东西不一样，**角色本身就不同**：

| | 群空间 | 个人空间 |
| --- | --- | --- |
| 它是谁 | 团队的 AI 员工 | 你的个人助理 |
| 负责人 | 拉它进群的人 + 建空间那一刻的群主/管理员（**一次性冻结**） | 你自己，唯一 |
| 成员 | 群里和它互动过的人 | 无 |
| 手和嘴 | 这个群 | 这条私聊 |
| 眼睛 | 本群；经授权可读别的空间 | **你在的任何群 —— 包括没有它的群** |
| 特有能力 | 项目跟进、反馈接单、方案对比 | **盯群**、todo 提炼、问答 |
| 谁能看到 | 空间成员 | 只有你 |

**「个人空间能盯没有机器人的群」是我们完全没有的形态**，是这份设计记录的核心待补能力。
它不是一个功能，是一种**授权模型**。

## 3. 委托：个人空间怎么把眼睛伸到别的群

机制就是个人授权（user token）：

1. 你在私聊里说「帮我盯着 X 群」（那个群里可以没有机器人）
2. 它拿**你的**身份去读那个群 —— 你能看到的它才能看到，这是天然的权限上限
3. 读到的东西只回到**你的私聊**，不会流去任何群 —— 手和嘴还在本空间
4. 授权会过期 → 这个群**单独**暂停，其他被盯的群不受影响
5. 暂停期间**游标不动**，重新授权后从上次的位置接着读

第 4、5 条就是截图里那张「关注的群聊授权已到期」卡片背后的全部设计。

我们现在的差距：
- `UserTokenStore` 有，但只用来「以你的身份读文档」，没用来盯群
- `routines` 的 `watch` 只能盯**机器人在的群**（读历史走的是应用身份）
- 授权过期是全局的，不是按被盯的群隔离
- 游标和授权状态没挂钩

改法不大：给 watch 职责加一个 `delegatedBy`（谁的授权），读历史时带这个人的 user token；
授权失效时只把这条 watch 标成 `suspended`，不动游标，给这个人发一张两步授权卡。

## 4. 执行环境要变成一等实体

目标设计：将**机器作为可挂载的执行资源**。目标机器通过配对流程连接，凭据留在各自环境；
用户确认后，可以在对话里指定执行位置，例如「把构建放到 gpu-box-1 上跑」。这一段是设计目标，不是当时的验收记录。

Friday 的现状是反过来的：它**就跑在**一台机器上，那台机器既是本体又是唯一的执行环境。
但其实已经有两个执行环境了，只是没抽象出来：
- 服务器上的沙箱（dsh 的 workspace）
- 用户自己的电脑（通过桌面桥）

所以这一条不是"从零做"，是**把已有的两个收进同一个抽象**：

```
ExecutionTarget = { id, kind: 'local' | 'attached' | 'desktop', name, status }
```

空间配置里选一个默认；对话里可以临时指定。好处不只是能跑构建 ——
**它同时解决了"开给同事之后，谁的活在谁的机器上跑"**：每个人的私聊空间可以挂自己的机器，
不用共用一台开发机、也不用共享 `repos/`。

## 5. 模型绑在空间上，不是绑在进程上

空间模型配置的目标包含三个角色：
- 默认模型
- **备用模型**（默认模型异常时自动兜底）
- **「判断什么消息该主动回」的专用模型**（便宜的那个）

第三个尤其聪明：主动判断是高频低价值的活，用大模型纯属浪费。

我们卡在"一个 dsh 进程一个模型"。这条我之前说是架构限制，现在看清楚了 ——
**限制在运行时，不在架构**。解法是把 `AcpRuntime` 从「一个 dsh」变成「按模型 key 的 dsh 池」：

```
runtime.sessionFor(space) → 按 space.config.model 找/起对应的 dsh 进程
```

进程按需起、闲置回收。备用模型就是第一次 prompt 失败后换一个 key 重试。

## 6. 提案统一成一个实体

现在有三种提案，三套实现：
- 职责提案（routines，proposed/active/ignored/expired + 72h）
- 技能提案（skills，另一套）
- 主动推送的「新提议」（还没有）

它们是**同一个东西**：某件事我想做，你点接受或忽略，72 小时没人理就作废。

```
Proposal = { id, kind: 'routine' | 'skill' | 'action', spaceId, title, payload,
             status: 'proposed'|'accepted'|'ignored'|'expired', proposedBy, expiresAt }
```

统一之后，「等你处理的提议」在 `/status` 里就是一节，不用分三处查。

## 7. 「它知道的事」要有一页人能翻的

记忆入口需要让用户查看从聊天中整理出的内容及其来源，知道 Friday 基于哪些历史信息工作。

我们有分层记忆、有 candidate/confirmed、有 `/memory` 命令 —— 但**没有一页给人翻的**。
在不做网页后台的前提下，这一页就是：每个空间一篇 wiki 文档（已确认的）+ 一张表（候选的，勾一下就是确认）。

## 8. 落地顺序

按「能不能解锁别的东西」排，不按工作量排：

1. **委托盯群**（§3）—— 解锁个人空间的核心价值，也是开给同事之后每个人最先想要的
2. **提案统一**（§6）—— 小，但统一之后后面所有「我建议…」都走同一条路
3. **执行环境抽象**（§4）—— 开给同事的第二个前置（第一个是 `repos/` 隔离，已做）
4. **按空间选模型**（§5）—— 要动运行时，但省钱且解锁"主动判断用便宜模型"
5. **「它知道的事」那一页**（§7）—— 表格版后台的一部分
6. 边界那句话进文案（§0）—— 十分钟的事，但决定了人敢不敢把它拉进群

## 9. 不抄的

- **网页后台**：判断标准仍然是「第二个人开口问"我怎么看我自己的职责"」（见上一轮讨论）
- **多租户**：部署在单个飞书租户内，不做多租户隔离
- **多智能体拓扑**：根据实际任务与权限边界决定是否拆分，不为增加智能体数量而拆分。
