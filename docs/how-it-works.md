# Friday 的上下文、权限、记忆与功能边界

这篇讲 Friday 现在是怎么转的：上下文、权限、记忆不是三个功能，是三套贯穿全身的机制，
不说清楚，后面每个功能该挂在哪都说不明白。

结论先行，三句：

1. **上下文不是"塞得多"，是"分层 + 按需拉"。** 塞进 prompt 的只有"判断该去拿什么"所需的东西，
   真正的内容（群历史、文档、代码）全靠模型自己调工具现拿。
2. **权限是三条正交的轴**，不是一张权限表：用谁的 token 读、谁能改这个空间、执行侧沙箱放不放行。
   三条各管各的，任何一条都不能用另外两条替代。
3. **记忆的核心不是存储，是 `candidate` / `confirmed` 两态分离。** 有了它，模型才敢自动记；
   没有它，自动记忆迟早污染人工结论，然后你就再也不敢信它了。

## 一、上下文

### 1.1 五层，各有各的失效方式

| 层 | 放在哪 | 什么时候变 | 代码 |
|---|---|---|---|
| 持久指令（角色/硬规则/工具用法/说话方式） | 工作区的 `AGENTS.md`，dsh 自动加载 | 几乎不变 | `workspaceInstructions()` |
| 本轮上下文头（位置/发言人/时间/会话/联盟） | 用户消息开头 | 每轮 | `buildTurnPrompt()` |
| 空间偏好（简短/详细 + 负责人写的注意事项） | 同上，紧跟上下文头 | 负责人改才变 | `spacePrefsBlock()` |
| 记忆（常驻要求 + 本轮相关的笔记） | 同上 | 每轮检索 | `composeForPrompt()` |
| 会话历史 | dsh session 自己的上下文 | 同话题内累积 | `sessionKey` |

**为什么指令放 `AGENTS.md` 而不是每轮 prompt 里**：它是稳定前缀，KV cache 能命中。
每轮都变的东西（时间、发言人）如果混进去，前缀就碎了，每轮都要重算。
这不是洁癖，是成本——B 端每人每天几十轮，前缀一碎就是几倍的钱。

**首轮和追问不一样**：首轮会把话题里**在触发消息之前已有的消息**（`priorThreadMessages`）塞进去，
因为模型还不知道大家在聊什么；追问继续使用同一 dsh 会话。话题历史保留机器人回复，
读取失败或截断时会明确标记，不能把没读到当作没有发生。空间偏好和本轮检索出的记忆每轮注入，
所以新记忆和设置变更在追问中也能生效，`/why` 与实际注入内容一致。

### 1.2 不在 prompt 里的那一大半

群历史、文档正文、代码、日程、GitHub issue——**一个字都不预先注入**。
模型看完上下文头，自己决定调哪个工具去拿：`feishu_read_thread` / `feishu_search_messages` /
`listChatHistory` / `repos/` 里 grep / `github_get_issue`。

这是刻意的取舍。反面做法是"把这个群最近 200 条都塞进去"，看起来省事，实际上：
上下文被无关内容占满、模型抓不住重点、每轮成本恒定地高、而且**没法解释**——
你问"你怎么知道的"，它只能说"你给我的"。
现在的做法是每次拿什么都留痕（ContextReceipt），`/why` 能原样答出来。

### 1.3 上下文的硬边界

写在 `AGENTS.md` 的硬规则里，同时在工具层真的做了约束（**不靠模型自觉**）：

- 群会话只能读本群；本群加入了"联盟"时能读同联盟的群，上下文头会列出来。
- 私聊会话能读**发起人也在**的其他群——用他的 token，见下一节。
- 私聊里读到的东西不能原样贴回群里。

**可读不等于可导出。** PMO 只投影绑定群自己的事项；私聊不能使用 PMO，群里也不包含其他群、联盟和企业层。
建表、重绑和手动同步需要本群负责人或管理员，自动同步会复核配置者权限。每群独立绑定，
不同群不能共享同一个多维表格 base；外部表格的读者权限由负责人管理，Friday 不声称已验证全部受众。

`/selfcheck` 只统计当前群，或当前私聊中本人的任务。任务记录包含请求正文和错误，不能作为
无敏感内容的全局数据使用；全局定期自检及自动写企业级教训已停用。

## 二、权限：三条正交的轴

### 轴一 · 用谁的身份去读（可见性）

整个可见性模型就是代码里反复出现的这一行：

```ts
const as = msg.chatType === 'p2p' && msg.senderOpenId && userTokens
  ? await userTokens.accessTokenFor(msg.senderOpenId)
  : undefined
```

- **群里**：永远是应用身份（tenant_access_token）。
  个人授权**不会**让 Friday 在群里多看见任何东西——这一条必须能对同事讲清楚，
  否则没人敢授权。授权卡上那句"群里我仍然只用机器人身份"就是在说这件事。
- **私聊**：本人授权过就用 **user_access_token**，于是能读他在的群（哪怕 Friday 不在那个群）、
  他的单聊、他有权限的文档。没授权就退回应用身份，能力自然收窄。
- **盯群**：用委托人的 token 去读一个 Friday 根本不在的群。所以委托授权一到期，
  那个群就必须停——这是为什么要有橙色的"授权到期"卡。

### 轴二 · 谁能改这个空间（policy.decide）

- 空间负责人 = **拉我进群的人** ∪ **建空间那一刻的群主/管理员**，然后**冻结**。
  冻结是关键：后来换群主不影响，后来退群也还算。
  不冻结的话，负责人集合会随群成员变动漂移，某天突然没人能改设置，或者突然多出一堆人能改。
- admin 是全局的，写在配置里。
- 唯一入口 `policy.decide({ spaceId, openId, action })`。没有第二条路径——
  这条很重要，否则权限判断会散落到二十个地方，改一次漏三处。

### 轴三 · 执行侧放不放行（permissions.ts）

dsh 的 ACP 桥有个坑：`session/request_permission` 只带 `toolCallId`，不带工具名、不带参数。
所以 Friday 得自己**先记住每个 tool_call 的 rawInput**，收到权限请求时按 id 找回来，
再按工具名归类成 execute / edit / read，把命令原文和模型自己写的 `justification`
印在确认卡上发给**发起人**。

工具过程只保留在网关内部，不再发进度卡或任务结束后的撤回提示。运行状态用表情反馈，
需要授权时仍单独发送确认卡，完成后发送正文、折叠结果或文档链接。

两个细节：
- 群里别人点确认不算（`pending.approverOpenId` 校验），只有发起人和可信用户能放行。
- `repos/` 是全局共享检出，挂进谁的工作区谁就能读所有仓库，所以**默认不挂**（`reposAllowed`），
  白名单 + 管理员 + 显式开过的群才有。把应用开给同事之前，这一条是前置。

### 轴四（不是权限，但常被当成权限）· 飞书后台的可用范围

应用后台的「可用范围」和「数据范围」是另一回事，改了要发版审批才生效。

## 三、记忆

这部分说明身份、来源和可见范围如何共同约束上下文。

### 3.1 存储

SQLite 一张 `memory_notes` + FTS5（`tokenize='trigram'`，所以中文搜得动）。
没有向量库。原因：几千条量级下 trigram + bm25 够用，而且**可解释**——
能指着说"命中的是第 17 号笔记"，向量召回做不到这件事。

### 3.2 四层作用域：写的时候必须显式打标，读的时候按身份取集合

| 作用域 | 含义 | 谁能读 |
|---|---|---|
| `space:sp_dm_<open_id>` | 个人 | 只有本人 |
| `space:sp_xxxxxxxx` | 空间 | 空间成员 |
| `circle:<name>` | 联盟 | 同联盟的群 |
| `org` | 企业 | 全员，写入要晋升 |

**空间作用域和 chat 解耦**，所以群换绑、群重建，记忆都不丢。
这是当初把 `space` 抽出来的唯一理由，现在看是对的。

`promote()` 做晋升（群 → 空间 → 企业），原条目保留，来源里记"从哪来的"，且会查重。

### 3.3 三态：整件事的地基

```
candidate  ──人确认 / 模型按人的明确要求记──▶  confirmed
    │                                              │
    └──────── 夜间整理可以删/合并 ────────┘  夜间整理绝对不许碰
                                               │
                                        被新结论替代 ──▶ superseded（不删，留痕）
```

- `candidate` = 模型自己从对话里推断的。注入 prompt 时**明确标"自动记录未确认"**，
  并要求模型引用时说明。
- `confirmed` = 人明确说的、人点确认的。
- `superseded` = 有了新结论，旧的不删，只是不再注入、不再检索。留着是为了能回答"你以前是不是记的别的"。

**为什么必须两态**：没有这个分离，你就面临一个二选一——要么不让模型自动记（那就没有持续学习），
要么让它自动记（那么它某天推断错一条，这条错误就和你亲口说的话平起平坐，
而且会一直注入下去，你还不知道是哪一条在作祟）。两态分离把这个二选一拆开了。

### 3.4 七种类型，其中一种特殊

`qa` / `fact` / `decision` / `todo` / `profile` / `rule` / `lesson`。

`rule` 特殊：它**不参与相关性检索，每个新会话无条件注入**。
"以后回答都简短点""这个群攒一批再处理"——这类长期要求如果走检索，
就会因为和当前问题不相关而被漏掉，然后人会觉得"我说过的你怎么又忘了"。
只在人明确说"以后都…"时才记成 rule，限 12 条。

### 3.5 三条写入路径

1. **主回答里**模型自己调 `friday_memory_save`。
2. **轮末反射**（`REFLECT_PROMPT`）：答案已经发出去之后，网关**自动追加一轮**，
   照 mem0 的 ADD / UPDATE / DELETE：先 `friday_memory_search` 查已有的，
   再决定新增还是 `replaces` 旧编号。最多 5 条，没得记就回 `NOTHING`。
   人完全看不见这一轮。
3. **夜间整理**（`buildConsolidatePrompt`，照 Anthropic 的 dreaming）：
   攒够 3 条 candidate 就触发，做三件事——合并重复、删掉没价值的、挑出值得人确认的，
   产出一张卡让人点。**硬规则写在 prompt 里：只动列出来的这些编号，不许碰任何 confirmed。**

这三条 + 三态，就是"持续学习"的全部机制。没有微调，没有向量库，
靠的是**分层 + 状态机 + 人在回路**。

### 3.6 可解释性不是附加功能

`composeForPrompt()` 除了返回文本，还返回 `MemoryUsage`：这一轮用了哪几层、
每层几条常驻规则、命中几条、分别是哪些编号。写进 ContextReceipt，`/why` 直接答。

这是刻意的：B 端场景里"它凭什么这么说"是个会被反复问到的问题，
答不上来的系统在公司里活不过三个月。

## 四、协作功能的实现与待补范围

按"已经有 / 能做但没做 / 结构上做不了"三档。**结构上做不了的一个都没有**——
这是好消息也是坏消息：没有技术壁垒，差距全是工作量。

### 4.1 已经有（✅）

| 功能 | Friday 当时的实现 |
|---|---|
| 空间在第一条 @ 时才建，进群不建 | ✅ |
| 群负责人 = 拉它进群的人 ∪ 建空间那刻的群主，冻结 | ✅ `adoptSpaceOwners` |
| 群聊换绑不丢东西 | ✅ space 与 chat 解耦 |
| 空间知识汇总页 | ✅ `friday_wiki` |
| 盯群（可盯它不在的群，用委托授权） | ✅ `friday_watch_add` |
| 私聊折叠摘要卡（一行结论 + 展开） | ✅ `collapsible_panel` |
| 常驻菜单（我的任务 / 关注的群聊 / 记忆 / 设置 / 使用说明 / 个人授权 / 重开会话） | ✅ 后台已配 |
| 授权卡两步 + 「完成授权」按钮 + 到期橙卡 | ✅ |
| 读得懂别人转发进来的整段聊天记录 | ✅ |
| 记忆分层 + 编号 + `/forget` / `/memory confirm` / candidates | ✅ 有对应数据结构与操作入口 |
| 提案 72 小时过期作废 | ✅ `expireProposals` |

### 4.2 差距清单（原来按"值不值得先做"排，现在标的是做完没有）

**第一档 —— 不做的话产品是残的：**

1. **巡查指令能用自然语言改写**（✅）。`friday_routine_update` +
   `POST /v1/routine/update` + `RoutineStore.update`。
   **只在 schedule 真的变了时才重算 `next_run_at`**——改个措辞不该把已经攒到的
   读取位置和下次运行时间冲掉；空字符串一律忽略，免得"只改名字"顺手把 prompt 清空。
   改完必须回读（写进 AGENTS.md）：改成了什么、下一轮什么时候跑、从哪一轮开始生效。

2. **Bug 收敛**（✅）。`bug_buckets` + `bug_reports` + FTS5 trigram。
   `similar()` **只给候选，不自动归并**——归错桶之后没人会去翻，等于把那条反馈删了。
   `stats()` 给 PMO 看板用。

3. **追问轮次预算**（✅）。`MAX_FOLLOWUP_ASKS = 3`（bug 追问）、`MAX_NUDGES = 3`（收件箱捎带）。
   `tryAsk` 在**返回允许之前**就记账——先扣再问，否则问出去了没记上，等于没有上限。
   骚扰一次，这个群就再也不欢迎机器人了。

**第二档 —— 体验差一截，但不致命：**

4. **统一收件箱 / 待拍板**（✅）。`inbox_items` + 回答末尾捎带。
   最多捎 3 次、两次之间隔 12 小时、刚建出来的先放 30 分钟——超过就是骚扰。
   `dueFor` 只读不记账，真发出去了才 `markNudged`：否则一条没发成的回复也会算他被提醒过。
   **群里只捎本空间的事**（`space_id` 过滤）——私聊里攒的事贴进群等于替人泄密。
5. **三档模型**（❌ **做不了，不是没做**）。`SpaceConfig.models` 和 `/space set model` 都在，
   但**读它的人不存在**：网关只连着一个 dsh 进程，模型是它启动时 `FRIDAY_MODEL` 定死的，
   ACP 协议里也没有按会话换模型的口子。真要分档得为每档各起一个 dsh 进程。
   所以 `/space set model` 现在会**明说"记下了，但还没生效"**——
   一个让人以为省了钱、其实没省的开关，比没有这个开关坏得多。
6. **沿用最近配置**（✅）。`user_defaults` 表；`repos` 不进默认值（那是权限，不是偏好）。
7. **行为偏好补全**（✅）。`ack` 使用 `react` / `none`：
   `react` 用表情反馈状态，`none` 连完成表情也不贴。旧 `card` 按 `react` 处理；过程卡已停用。`progressCardDelayMs` 及对应环境变量只为兼容保留，任何取值都不会启用过程卡。
   **但越权确认卡不受它管**——那是"我要干一件危险的事"在群里唯一的痕迹，不该被一条偏好关掉。
   `digestEveryMs`、`proactive.hours` 同样落库并生效。
8. **盯群授权到期卡真的发出去**（✅）。`routines.run_as` 就是那个 `delegatedBy`——
   委托给谁跑、到期该找谁重新授权，是同一个字段。链路：
   `runRoutineFresh` → `watchAuthExpired(routine, runAs)` → `suspendForExpiredAuth` 把这个人的盯群全停掉
   → 橙卡**每人只发一次**（`authcard:<openId>` 挡重复）→ 同时进收件箱，
   之后蹭他的下一次对话再捎一句 → 网页回调、粘贴回调和完成按钮统一调用 `resumeAuthorizedRoutines`。
   凭据可用且空间仍启用、绑定未变时，恢复因授权到期暂停的关注职责；手动停用和空间停用保持原状。
   保留读取游标，按当前权限和可取得的历史继续读取；不承诺历史完整。
9. **接入自己的机器**（❌，故意先不做）。`exec_targets` 表没建。
   这条一旦做了，Friday 就能在别人的机器上执行命令——权限模型要重新想一遍，
   不该跟这批一起顺手上。

**第三档 —— 靠模型，固化了更稳但不急：**

10. 分类从数据里长出来（功能 bug / 排版密度 / 内容保真）而不是固定枚举 —— 现在靠模型临场分，能用。
11. 每条带深链（→ 查看产物）—— 取决于数据源本身有没有链接，有就能带。
12. 角色判断带证据（"发言量第一（50 条）"+ 原话引用）—— skill 里写了，**还没实测过**。

### 4.3 一个我之前想错了的地方

"报 bug → 主动 @ 对应的人"这条链卡在了 `identities` 表上
（GitHub login ↔ 飞书 open_id 的映射），理由是"不建映射就找不到人"。

这个判断需要补充：**群内行为**也可以提供责任人线索，例如谁持续回答该模块的问题、原话是什么。
这类线索不依赖 GitHub 映射，但需要保留证据，不能把推断直接写成正式指派。

所以这条链有两条路，应该都走，而且**路 B 先上**：

- **路 A**（要 `identities` 表）：`git log` / PR 作者 → GitHub login → 飞书 open_id。
  准，但对"这人没关联过 GitHub"直接失效，而这在公司里是常态。
- **路 B**（不需要任何新表）：这个模块的问题过去都是谁在群里答的 → 他就是事实上的 owner。
  用 `feishu_search_messages` + 群历史就能算，**今天就能做**，而且对没关联 GitHub 的人同样有效。

两条都拿不到结论时，`bug-triage` skill 里那条硬规矩仍然成立：**查不到人就不 @**。

## 六、所以先做什么

按"缺了它产品是残的"排，前三件：

1. `friday_routine_update` —— 盯群/定时任务的指令能用一句话改，改完回读、说清何时生效。
2. Bug 收敛桶 —— 新反馈归并到已有桶或开新桶，桶有状态和计数。这是 PMO 那条线的地基。
3. 追问轮次预算（至多三轮）—— 小改动，但它是主动模式敢不敢开的开关。

再之后是 `routines.delegatedBy`（解锁到期卡）、`user_defaults`（沿用最近配置）、
`SpaceConfig.models`（主动判断专用小模型，省钱）。

`identities` 表**降级**：不再是"@ 对应的人"的前置，路 B 今天就能跑。
