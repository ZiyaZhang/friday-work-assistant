## 问题和可见结果

原 `ChangeManager.publish` 固定首次发布快照和意图，可靠处理开 PR 结果未知，但在 review 后重新修改文件会被拒绝。`github_pr_diff` 又只读文件与 review 首批，漏掉行内评论，review 请求失败被写成空数组。

预期自然语言流程：用户要求继续改原 PR → 找回原目录 → 核对最新提交和评审 → 修改、验证 → 确认本次快照 → 同分支追加提交 → 回原 PR 链接。收到查询不会创建修改目录；review 只读不会自动发布。PR 正式状态继续以 GitHub 为准。

## 应用接口

| 工具 / API | 职责 |
| --- | --- |
| github_list_changes / change/list | 当前会话、发起人、工作根下的登记修改；含目录、分支、PR 和发布阶段。不是实时 GitHub 状态。 |
| github_pr_diff / pr/diff | 准确 head/base SHA、diff、reviews、行内评论，分别标记覆盖范围。 |
| github_open_pr / change/publish | 保持首次发布契约和原收据，不承接后续新快照。 |
| github_update_pr / change/update | inspectUpdate 取增量和父提交，确认后 updatePr 发布同一 PR 的新提交。title/body 仅作为 commit 内容，不隐式修改 PR 描述。 |

API 在访问前、异步读取后、确认后和外部写入前沿用当前执行、空间、来源仓库授权；模型不能指定父提交、发布身份或推送目标。审批的文件列表是相对最近已确认 head 的新增变化。

## 状态和恢复

保留 `github_changes` 的首次发布快照及收据。`github_change_updates` 只记每次追加的父提交、完整树、内容意图、新提交和发布结果；不是另一份工作事项表。最近一次已确认追加提供下一次父提交。

同 change 的首次发布和追加共用串行队列。新提交唯一父节点是已确认 head；推送对精确 ref 做比较后更新，不能覆盖后来的人类提交。PR 必须属于登记仓库与分支，且仍开启、未合并。

推送尚未开始的授权或凭据失败可再次尝试。推送启动后结果未知，保留原操作；重启或重复调用只读核对远端 ref 和 PR head，均为本次提交才确认。没有核实之前不能换快照绕过，也不创建第二个 PR。初次 PR 创建结果未知时不进入追加流程。

## 读取覆盖

reviews、行内评论、文件各自分页并有上限；已读部分与失败来源分别返回。patch 按 UTF-8 字节预算截断，缺 patch 也标缺口。没有读取到不能报“没有评审意见”，旧评论不能直接当当前版本缺陷，行内评论不等同于 unresolved thread。

## 验收

1. 真实本地 Git、SQLite、HTTP、MCP：首次 PR → 两条评审要求 → 同 PR 新提交；父节点正确、正文不变、PR POST 仍一次。
2. 并发、撤权、审批后文件变化、远端推进、已合并/关闭：不覆盖远端，保留本地成果。
3. 推送成功后本地确认失败、重启及重复调用：精确恢复同一提交；unknown 不换意图或重复开 PR。
4. review 超一页、行内评论、读取失败与 diff 预算：结果和覆盖标记一致。
5. 独立评审、相关及全量工程回归；之后真实模型工具选择、真实 GitHub 与飞书分别验收。前四项不冒充第五项。

剩余阶段 4 范围：反馈/Issue/修改目录/原消息的宿主绑定、跨会话接续授权、GitHub 后续事件唤醒、真实反馈到可评审 PR 的平台验收。本片不增加多 Agent 编排或通用事件框架。
